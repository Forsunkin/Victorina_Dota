# Dota 2 Build Quiz

Легковесная браузерная викторина: по предметам из **реального матча Dota 2** нужно угадать героя.

> **Статус:** проектирование. Существующие Python-скрипты — ранний прототип; пока не удаляем их и не считаем продуктовой реализацией.

## Цель проекта

- Максимально лёгкие клиент и сервер, минимум памяти, CPU и трафика.
- Все игровые действия, таймеры и переходы между вопросами выполняются на стороне браузера.
- До старта партии клиент загружает весь необходимый набор вопросов и изображений. Во время партии, даже многочасовой, **нет сетевых запросов**.
- Развёртывание на произвольном Linux-хосте/VM/VPS с помощью контейнера и настраиваемого порта.
- Источник вопросов — реальные матчи; впоследствии регулярный автоматический сбор, фильтрация и краткосрочное хранение.
- **Разрабатывать и выпускать по версиям**, добавляя новые возможности постепенно, а не строить всю систему сразу.

| **v0.2 — Качество и интерфейс** | Улучшить визуализацию, навигацию, предзагрузку и локальное кеширование ресурсов; исключить дубли заданий и проверить автономность | Нет рекордов и автоматического обновления |
| **v0.3 — Хранение** | SQLite на сервере, импорт вручную подготовленных пакетов, дедупликация, сроки хранения и замена набора данных | Нет автоматического получения матчей |

Версии — план, содержание можно корректировать по результатам тестирования. Каждая версия должна быть запускаемой и пригодной к проверке самостоятельно.

## Ближайший этап: v0.1

**Не создавать полноценный backend заранее.** Для первого релиза достаточно статического HTML + CSS + JavaScript и компактного сервера раздачи файлов внутри контейнера. В дальнейшем серверную часть планируется реализовать на Go с SQLite.

### Подготовка набора данных

1. **Разово** получить около **5000 исходных строк/записей** из реальных матчей. Это целевой размер сырой выборки, а не гарантированное число готовых вопросов.
2. **Локально, на домашнем компьютере**, проверить/отфильтровать записи: корректность героя и предметов, качество матча, полнота сборки, дубли, совместимость ID со справочниками.
3. Преобразовать прошедшие фильтр строки в **готовый статический файл** (например, `questions.json`) с числовыми ID. Сохранить `match_id` для прослеживаемости.
4. Подготовить локальные справочники героев и предметов и необходимые изображения.
5. При обновлении подборки **вручную подменять файл заданий** и при необходимости справочники/изображения; пересобирать контейнер или подключать данные томом — определить при реализации.

Под словом «база» в v0.1 понимается **готовый файл с заданиями**, а не обязательная СУБД. SQLite появляется только в v0.3. Браузер **не обращается к OpenDota**, а получает только подготовленные локальные данные.

### Поведение первой игры

- Игрок открывает страницу, а браузер получает необходимые файлы и пул вопросов.
- Игра показывает реальные предметы героя, игрок выбирает героя и узнаёт правильность ответа.
- Переход к следующему вопросу — локально, без запроса к серверу. Локальный таймер можно использовать для автоматического перехода.
- В одной партии не повторяем уже показанные вопросы, пока доступны новые.
- **Пока нет очков, счёта, таблиц рекордов, системы трёх ошибок и глобальной статистики.**
- До начала партии клиент должен завершить загрузку требуемых ресурсов; после этого игровой процесс работает без сети.

### Критерии готовности v0.1

- Игра открывается через браузер с адреса и порта контейнера.
- Можно последовательно отвечать на вопросы из вручную подготовленного набора.
- Все картинки показываются из локально обслуживаемых ресурсов; никаких обязательных внешних CDN.
- После загрузки отключение интернета не прерывает текущую партию; в Network нет запросов при переходах между вопросами.
- Замена набора вопросов не требует изменения игрового JavaScript.
- Нет лишних серверных сервисов, СУБД и задач периодического опроса API.

## Предварительный технологический стек

- **v0.1–v0.2:** HTML, CSS, Vanilla JS; статический JSON и изображения; простой HTTP-сервер внутри Docker.
- **v0.3+:** SQLite для хранения и индексов.
- **v0.4+:** Go (`net/http`) для API; один процесс без Redis, Celery и очередей.
- **v0.5+:** отдельный логический модуль фонового сбора матчей внутри приложения, с изоляцией ошибок и лимитами источника.
- **Кеширование:** Cache API/Service Worker или другое локальное хранение после проверки потребностей; данные должны быть согласованы по версии.

## Решения, которые пока не фиксируем

- Порог качества матча, допустимые игровые режимы, распределение по рейтингам.
- Точный набор предметов на экране: 6 основных слотов, нейтральный слот, рюкзак.
- Источник и лицензирование игровых изображений, формат картинок.
- Формула сложности и правила начисления очков будущих версий.
- Размер порции вопросов, условия завершения партии и механизм защиты рекордов.

## Принципы разработки

1. Сначала работоспособный и проверяемый минимум; усложнение — отдельными версиями.
2. Источник матчей, хранилище и frontend должны быть слабо связаны.
3. Сетевое общение разрешено **до начала и после окончания партии**, но не требуется в процессе.
4. Обновление патчей Dota 2 не должно ломать уже загруженную партию; справочники и задания версионируются.
5. Текущий код — полезный источник идей и прототипы, а не ограничение будущей структуры.
